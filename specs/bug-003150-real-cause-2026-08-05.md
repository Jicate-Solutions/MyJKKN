# BUG-003150 / BUG-003151 — real cause

**Date:** 2026-08-05 · **Mode:** read-only investigation · **No production writes, no PR, no bug closed.**

## VERDICT

The real cause **is** the `new Date("YYYY-MM-DD")` UTC-midnight parse that PR #2667 already fixed — the reporter's browser was in a timezone **behind UTC**, not IST, which the recorded console logs prove directly; the fix is merged and deployed, but the *same defect survives unfixed in three other browser-side call sites*.

This contradicts the brief's premise. The brief measured the fix as inert **in Asia/Kolkata** and concluded the cause was still unfound. That measurement is correct but it does not apply: this reporter was not in IST.

## The evidence that settles it

`bug_reports.console_logs` recorded the failing lookup verbatim.

```sql
SELECT display_id,
       (SELECT string_agg(e->>'message', E'\n')
        FROM jsonb_array_elements(console_logs) e
        WHERE e->>'message' ILIKE '%day data%'
           OR e->>'message' ILIKE '%Period slot not found%') AS warn
FROM bug_reports WHERE display_id IN ('BUG-003150','BUG-003151');
```

**BUG-003150** → `No day data found in timetable {"dayKey":"SUNDAY","availableKeys":["FRIDAY","MONDAY","TUESDAY","THURSDAY","WEDNESDAY"]}`

The URL carried `date=2026-03-23`. **2026-03-23 is a Monday.** The deployed code computed `SUNDAY` — shifted back exactly one day. `new Date("2026-03-23")` is UTC midnight; `toLocaleDateString` renders it in the *browser's* zone. Rendering as Sunday requires a strictly negative UTC offset. In IST (+5:30) it renders 05:30 Monday and the bug cannot occur. This is not inference from code — it is the runtime value the browser logged.

**BUG-003151** → `Period slot not found in day data {"periodId":"d04c8826-…","availableSlots":["5a172a91-…","75dc5286-…","bd68186d-…","d4a3bff4-…"]}`

Same cause, different symptom. `date=2026-03-25` (Wednesday) shifted to TUESDAY, which *does* exist as a key — so it passed the day guard at `page.tsx:734` and failed one step later at the slot match (`page.tsx:757`).

Why that must be a wrong-day read: the data is intact.

```sql
SELECT d.key AS day_key, s.pkey AS object_key, s.value->>'slot_id' AS slot_id,
       s.value->>'primary_staff_id' AS primary
FROM timetables t, jsonb_each(t.timetable_data) d(key,value),
     jsonb_each(d.value) s(pkey,value)
WHERE t.id='b141cb5e-54ed-4fec-8401-222d641fbaaf'
  AND s.value->>'slot_id'='d04c8826-6baa-4312-85c9-30cf466a2410';
-- WEDNESDAY | d4a3bff4-… | d04c8826-… | 199c0bea-… (team member IS assigned)
```

WEDNESDAY holds a slot whose `slot_id` equals the URL's `periodId`, with a team member assigned. The `slot_id` fallback loop (`page.tsx:747-756`) existed in the deployed tree on 2026-03-25, two days *before* the report (`git show 881ea895aa`). Had the code read WEDNESDAY, it would have matched. It did not match ⟹ it read a different day. The only input controlling that is `dayKey`.

Note the `availableSlots` fingerprint is useless for identifying the day: **every** weekday in this timetable has the identical object-key set (`5a172a91, 75dc5286, bd68186d, d4a3bff4`) because those keys are period-master ids (both bugs are period "CNR T6", 14:45–15:30). Only `slot_id` varies per day. That is also why the failure looks like missing data rather than a wrong-day read.

## Candidates ruled out with data

| # | Candidate | Verdict |
|---|---|---|
| 1 | Day-key case/format mismatch | **Dead.** 290/290 regular timetables key `WEEKDAY_UPPER`; code emits `.toUpperCase()`. Byte-identical. |
| 2 | Empty `selected_days` / `timetable_data` | **Dead for these bugs** — both slots carry a team member. Fleet-wide 163/8,122 regular slots (2.0%) genuinely have none. |
| 3 | Wrong IDs / RLS denial on `staff` | **Dead.** All 279 distinct regular-format ids resolve to real `staff` rows (0 missing). Every role holding `academic.attendance.mark` also holds `staff.view`, so `staff_select_scope_aware` is satisfied. |
| 4 | `attendance_mode` branch | **Dead.** Both timetables are `timetable_format='regular'`. |

## Residual defect — unfixed, same class, browser-side

PR #2667 fixed one call site. Three others still derive a weekday key from a UTC-parsed date string, and all three run in the browser (each imports `createClientSupabaseClient`):

- `lib/services/academic/attendance-faculty-sync.ts:40-42` and `:276-278` — the second feeds `timetable_data[dayOfWeek]` at `:280`, the exact lookup that failed.
- `lib/services/academic/attendance-dashboard-service.ts:534-537` — pending-attendance computation.

For any user whose machine is behind UTC these misread the day exactly as the mark page did. Fix is the same one-line transform. Sibling `attendance-dashboard-service.ts:382` already uses the safe `date + 'T00:00:00'` form. The range comparisons in `attendance-service.ts:1024/1087/1144` are safe — both sides parse identically.

## What remains unproven

1. **The reporter's actual timezone.** Forced by elimination (offset < 0), not observed — no TZ field is captured. Worth adding to the bug SDK payload.
2. **Whether both reports came from that one machine.** Both were filed within 5 minutes by the same reporter, so one misconfigured client may explain the whole cluster.
3. **Whether any IST user ever hit this.** No mechanism found by which they could; no other bug in the table shows a shifted `dayKey`.

## Why no PR was opened

The proven cause is already fixed and deployed. A PR "fixing" it would be a no-op and would misrepresent the state. The residual call sites are real but sit in different files and features — that is separate, clearly-scoped work needing its own authorization.

**BUG-003150 and BUG-003151 remain open pending human verification.**

# Addendum — cycle-format hypothesis: REFUTED for these bugs, but real elsewhere

*(Second round, commissioned separately. The finding above is unchanged at 877 words.)*

The proposal: `cycle`-format timetables key `timetable_data` by `cycle-N`, not weekday, so any weekday-key lookup returns `undefined`. **The mechanism is real and verified** — Arts & Science (Aided) timetables show `day_keys = cycle-1…cycle-6` while `selected_days` holds weekday names. But it is **not** the cause of BUG-003150/003151, refuted three independent ways:

1. **Both bug timetables are `timetable_format='regular'`**, not cycle (`dc9fb459`, `b141cb5e`, both created 2026-03-20).
2. **Their institution has zero cycle timetables** — JKKN College of Nursing and Research: 146 regular, 5 batch, **0 cycle**.
3. **The browser's own log lists weekday keys as available**: `availableKeys:["FRIDAY","MONDAY","TUESDAY","THURSDAY","WEDNESDAY"]`. A cycle timetable would have logged `cycle-N`.

**Q1 — does `loadStaff()` branch on format?** Yes. `page.tsx:689` reads `timetable_format`; `:691` batch, `:704` cycle → `dayKey = cycle-${cycleNum}` at `:719`, `:720` regular. The cycle branch was added 2026-06-17 and its comment describes this exact failure. Already fixed there.

**Q2 — blast radius.** 65 of 434 timetables (15%) are cycle, confined to 3 institutions: Arts & Science (Self) 39, Arts & Science (Aided) 25, Testing 1. Every other institution is 0.

**Q3 — have cycle timetables accumulated attendance?** Yes — **998 rows across 34 cycle timetables**, 677 since July 2026, latest 2026-08-05. Cycle marking works in production today. (Caution: `period_slot_id` is NULL for **all** 10,869 rows in every format, so it is not a usable discriminator.)

**Where the mechanism IS still live.** `attendance-faculty-sync.ts` and `attendance-dashboard-service.ts` contain **zero** references to `timetable_format` and index `timetable_data[dayOfWeek]` unconditionally (`faculty-sync:280`). These are the same two files already flagged above for the UTC parse — so each carries **two** defects. `attendance-dashboard-service` feeds the pending-attendance dashboard, statistics cards and the escalation service, so for the 65 cycle timetables it likely under-reports scheduled periods for both Arts & Science colleges. That is a separate, larger bug than either ID here, and worth its own investigation.
