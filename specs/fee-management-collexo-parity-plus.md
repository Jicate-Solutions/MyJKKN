## Fee Structure Complexity (JKKN Reality)

JKKN's fee structure is a **multi-dimensional matrix**. Every student's bill is the intersection of:

```
Fee = f(institution, program, academic_year, admission_type, scholarship_tier, fee_component)
```

### Dimensions

| Dimension | Examples | Impact |
|-----------|----------|--------|
| **Institution** | Engineering, Pharmacy, Arts & Science, Nursing, Education | Different fee schedules per campus |
| **Program** | B.E. CSE, B.Pharm, B.Sc. Nursing, M.Ed., MBA | Each program has its own fee structure |
| **Academic Year** | 2024-25, 2025-26, 2026-27 | Fees change year-over-year (tracked for audits) |
| **Admission Type** | Government quota, Management quota, NRI | Same program, wildly different fees |
| **Scholarship Tier** | Merit (100%), Merit (50%), Sports, SC/ST, OBC, Institutional | Reduces specific fee components |
| **Fee Component** | Tuition, Hostel, Transport, Lab, Library, Exam, Caution deposit | Each has its own amount and rules |

### Regulatory Constraints

- **State Fee Committee** sets maximum tuition for government quota seats
- **AICTE/UGC** norms on what can/cannot be charged
- Fee hikes must be justified and documented (NAAC audits)
- Government scholarship (NSP, state schemes) integration needed eventually

### What This Means for the Data Model

The existing billing tables use a 3-level hierarchy (`billing_parent_categories` → `billing_sub_categories` → `billing_item_categories`) to define fee line items. However, there is **no single table** that groups these into a named "fee structure" — we need a wrapper table plus an additional layer that maps fee structures to the multi-dimensional matrix above.

> **DB Reality (verified):** There is NO `billing_fee_structures` table in the current database. The table must be created as part of Phase 1 (see section 1.0 below).

A student's bill is generated by:

1. Look up student's institution + program + year + admission type + scholarship
2. Find the matching fee matrix entry → linked fee structure
3. Get the fee structure's items (from the existing hierarchy)
4. Apply scholarship reductions to specific components
5. Apply regulatory caps if applicable
6. Generate itemized bill

> **Column mapping (verified against live DB):**
> - Spec uses `admission_type` → maps to `learners_profiles.quota` (text) + `learners_profiles.entry_type` (text) in the actual database. During implementation, derive `admission_type` from these two columns.
> - `learners_profiles` is the **canonical student table** for all billing FKs. It has `id` (uuid), `institution_id`, `program_id`, but NO `user_id` column (see Phase 0 for auth mapping).
> - Student lookup: `learners_profiles.id` is the FK target for all `student_id` columns in billing tables.

## Phase 1: Fee Configuration Engine

This is the **foundation** everything else builds on. If the fee configuration can't model JKKN's reality, nothing else matters.

> **Convention: `student_id` FK target.** All new `billing_*` tables use `student_id uuid REFERENCES learners_profiles(id)` as the canonical FK for student references. The legacy `students` table FK is NOT used. Existing tables like `billing_student_bills` already reference `learners_profiles(id)` — this convention makes it explicit.

### 1.0 Fee Structure Wrapper

**New table: `billing_fee_structures`**

A grouping table that represents a named fee structure (e.g., "B.Tech Government Quota 2026-27"). The actual fee line items come from the existing hierarchy (`billing_parent_categories` > `billing_sub_categories` > `billing_item_categories`) and are linked via `billing_fee_structure_items`.

```sql
CREATE TABLE billing_fee_structures (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  institution_id uuid NOT NULL REFERENCES institutions(id),
  name text NOT NULL,                              -- "B.Tech Govt Quota AY 2026-27"
  description text,
  is_active boolean DEFAULT true,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);
```

**New table: `billing_fee_structure_items`**

Join table linking a fee structure to specific fee line items from the existing category hierarchy.

```sql
CREATE TABLE billing_fee_structure_items (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  fee_structure_id uuid NOT NULL REFERENCES billing_fee_structures(id),
  item_category_id uuid NOT NULL REFERENCES billing_item_categories(id),
  amount decimal(12,2) NOT NULL CHECK (amount >= 0), -- Amount for this component in this structure
  is_mandatory boolean DEFAULT true,               -- Can student opt out? (e.g., hostel for day scholars)
  display_order int DEFAULT 0,
  created_at timestamptz DEFAULT now(),
  UNIQUE(fee_structure_id, item_category_id)       -- Each item appears once per structure
);
```

> **How it fits together:** `billing_fee_structures` groups line items into a named structure. `billing_fee_structure_items` maps which items (from the existing 3-level category hierarchy) belong to each structure and at what amount. Then `billing_fee_matrices` (below) maps which structure applies to which program x year x admission_type combination.

### 1.1 Fee Structure Matrix

**New table: `billing_fee_matrices`**

Maps the multi-dimensional fee reality to the fee structure grouping table.

```sql
CREATE TABLE billing_fee_matrices (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  institution_id uuid NOT NULL REFERENCES institutions(id),
  academic_year_id uuid NOT NULL REFERENCES academic_years(id),
  program_id uuid NOT NULL REFERENCES programs(id),
  admission_type text NOT NULL                   -- Maps to learners_profiles.quota + entry_type
    CHECK (admission_type IN ('government', 'management', 'nri', 'lateral', 'spot', 'other')),
  fee_structure_id uuid NOT NULL REFERENCES billing_fee_structures(id),
  regulatory_cap_id uuid REFERENCES billing_regulatory_caps(id),  -- NOTE: Forward reference — create billing_regulatory_caps BEFORE this table, or add this FK via ALTER TABLE after both tables exist
  is_active boolean DEFAULT true,
  notes text,
  created_by uuid REFERENCES profiles(id),
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now(),
  -- A program + year + admission type can only have ONE fee structure per institution
  UNIQUE(institution_id, academic_year_id, program_id, admission_type)
);
```

**Why this table exists:** The **new** `billing_fee_structures` table (defined in section 1.0 above) defines fee line items. This matrix table maps WHICH fee structure applies to which combination of program × year × admission type. When generating a bill for a student, the system:
1. Gets student's program, year, and quota/entry_type from `learners_profiles`
2. Maps to `admission_type` (see mapping note below)
3. Looks up the matching `billing_fee_matrices` row
4. Gets the linked `billing_fee_structures` with its items
5. Applies scholarships and caps
6. Generates the bill

> **Column mapping — admission_type derivation rules:**
>
> `billing_fee_matrices.admission_type` is derived from the student's profile using these precedence rules:
>
> | `learners_profiles.quota` | `learners_profiles.entry_type` | → `admission_type` | Rationale |
> |---|---|---|---|
> | `government` | `regular` | `government` | Quota determines fee tier |
> | `government` | `lateral` | `government` | **Quota takes precedence** — govt quota lateral student pays govt fees |
> | `management` | `regular` | `management` | Standard management quota |
> | `management` | `lateral` | `management` | **Quota takes precedence** — mgmt quota lateral student pays mgmt fees |
> | (NRI flag set) | any | `nri` | NRI status overrides quota for fee purposes |
> | (spot admission) | any | `spot` | Spot admission has its own fee structure |
> | any | any | `other` | Fallback for unrecognized combinations |
>
> **Rule: Quota takes precedence over entry_type for fee determination.** A management-quota lateral-entry student pays management fees, not lateral fees. `lateral` as an `admission_type` value is only used when the institution has a specific lateral-entry fee structure distinct from both government and management.
>
> The `admission_type` column name is kept in the billing schema (not renamed to `quota`) because billing needs a broader set of values than `learners_profiles.quota` alone provides.
>
> **Implementation:** Create a helper function `deriveAdmissionType(studentProfile)` that encapsulates this mapping. All bill generation code calls this function — never derive admission_type inline.

### 1.2 Regulatory Fee Caps

**New table: `billing_regulatory_caps`**

Enforces state fee committee and regulatory body limits.

```sql
CREATE TABLE billing_regulatory_caps (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  institution_id uuid NOT NULL REFERENCES institutions(id),
  academic_year_id uuid NOT NULL REFERENCES academic_years(id),
  program_id uuid REFERENCES programs(id),       -- NULL = applies to all programs
  regulation_body text NOT NULL                  -- state_fee_committee, aicte, ugc, university
    CHECK (regulation_body IN ('state_fee_committee', 'aicte', 'ugc', 'university', 'other')),
  regulation_reference text,                     -- GO number, circular reference
  admission_type text                            -- NULL = applies to all types
    CHECK (admission_type IS NULL OR admission_type IN ('government', 'management', 'nri', 'lateral', 'spot', 'other')),
  -- Component-level caps
  max_tuition decimal(12,2),
  max_hostel decimal(12,2),
  max_transport decimal(12,2),
  max_exam decimal(12,2),
  max_other decimal(12,2),
  max_total decimal(12,2),                       -- Overall cap
  -- Approval documentation
  approval_date date,
  approval_document_url text,                    -- Uploaded GO/circular
  valid_from date NOT NULL,
  valid_to date,
  is_active boolean DEFAULT true,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);

-- Prevent duplicate caps for the same dimension (NULLs mean "applies to all")
CREATE UNIQUE INDEX billing_regulatory_caps_unique_dimension
  ON billing_regulatory_caps (
    institution_id,
    academic_year_id,
    COALESCE(program_id, '00000000-0000-0000-0000-000000000000'),
    regulation_body,
    COALESCE(admission_type, '__all__')
  );
```

**Enforcement:** When admin creates/edits a fee structure that's linked via `billing_fee_matrices`, the system checks against the regulatory cap and warns (or blocks) if limits are exceeded.

> **Implementation note:** Hardcoded `max_tuition`/`max_hostel`/`max_transport`/`max_exam`/`max_other` columns work for JKKN's known fee types. If custom fee components are needed in the future, add a child table `billing_regulatory_cap_items(cap_id, component_name, max_amount)` instead of adding more columns.

### 1.3 Scholarship Integration with Fee Components

**New table: `billing_scholarship_rules`**

Defines how scholarships reduce specific fee components.

```sql
CREATE TABLE billing_scholarship_rules (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  institution_id uuid NOT NULL REFERENCES institutions(id),
  scholarship_name text NOT NULL,                -- "Merit 100%", "SC/ST Tuition Waiver", "Sports Quota 50%"
  scholarship_type text NOT NULL
    CHECK (scholarship_type IN (
      'merit_full', 'merit_partial', 'sports', 'sc_st', 'obc',
      'minority', 'institutional', 'government', 'need_based', 'other'
    )),
  -- What it covers
  reduction_type text NOT NULL                   -- percentage, fixed_amount, full_waiver
    CHECK (reduction_type IN ('percentage', 'fixed_amount', 'full_waiver')),
  reduction_value decimal(8,2),                  -- 50.00 = 50% or ₹50 depending on type
  -- Enforce: full_waiver needs no value; percentage/fixed_amount require a positive value
  CHECK (
    (reduction_type = 'full_waiver' AND reduction_value IS NULL)
    OR (reduction_type IN ('percentage', 'fixed_amount') AND reduction_value IS NOT NULL AND reduction_value > 0)
  ),
  applies_to_components text[],                  -- {'tuition', 'hostel'} — which fee components
  applies_to_all_components boolean DEFAULT false, -- true = covers everything
  -- Prevent contradiction: if applies_to_all, don't also list specific components
  CHECK (NOT (applies_to_all_components = true AND applies_to_components IS NOT NULL AND array_length(applies_to_components, 1) > 0)),
  -- Eligibility
  min_percentage decimal(5,2),                   -- Minimum academic percentage
  max_family_income decimal(12,2),               -- Income ceiling
  eligible_admission_types text[],               -- {'government', 'management'}
  -- Duration
  valid_for_years int,                           -- How many years the scholarship lasts
  renewable boolean DEFAULT true,
  renewal_criteria text,                         -- e.g., "Maintain 75%+ attendance"
  -- Status
  is_active boolean DEFAULT true,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);
```

**Why separate from existing discount system:** The existing `billing_discounts` table handles ad-hoc discounts. This table handles **structured scholarship programs** that apply to cohorts of students with specific eligibility criteria. They work differently:
- Discount: Applied manually per student per bill
- Scholarship: Applied automatically based on student's scholarship assignment

> **Implementation note:** `applies_to_components` references fee component names as free-text strings. During implementation, these should be validated against actual `billing_item_categories.item_category_name` values (note: the column is `item_category_name`, not `name`). Consider migrating to a junction table with UUID references (`billing_scholarship_component_rules(scholarship_rule_id, item_category_id)`) instead of free-text matching.

### 1.3b Student Scholarship Assignments

**New table: `billing_student_scholarships`**

Maps individual students to the scholarship rules they have been awarded.

```sql
CREATE TABLE billing_student_scholarships (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  institution_id uuid NOT NULL REFERENCES institutions(id),
  student_id uuid NOT NULL REFERENCES learners_profiles(id),
  scholarship_rule_id uuid NOT NULL REFERENCES billing_scholarship_rules(id),
  academic_year_id uuid NOT NULL REFERENCES academic_years(id),
  awarded_date date NOT NULL,
  awarded_by uuid NOT NULL REFERENCES profiles(id),
  status text NOT NULL DEFAULT 'active'
    CHECK (status IN ('active', 'suspended', 'revoked')),
  revocation_reason text,
  priority int NOT NULL DEFAULT 1,                 -- Stacking order when multiple scholarships apply
  created_at timestamptz DEFAULT now(),
  UNIQUE(student_id, scholarship_rule_id, academic_year_id),  -- Prevent duplicate scholarship assignments
  UNIQUE(student_id, academic_year_id, priority)              -- Prevent duplicate priorities per student per year
);
```

> **Stacking rule:** When multiple scholarships apply to the same student, process in `priority` order (1 = highest priority, applied first). Each scholarship applies to the REMAINING amount after prior scholarships, not the original amount. Total reduction per fee component is capped at 100% — once a component reaches zero, remaining scholarships for that component are skipped.
>
> **Stacking pseudocode:**
> ```
> for each fee_component in bill:
>   remaining = component.original_amount
>   for each scholarship in student_scholarships ORDER BY priority ASC:
>     if scholarship.applies_to_all_components OR component.name IN scholarship.applies_to_components:
>       if scholarship.reduction_type == 'full_waiver':
>         reduction = remaining
>       elif scholarship.reduction_type == 'percentage':
>         reduction = remaining * (scholarship.reduction_value / 100)
>       elif scholarship.reduction_type == 'fixed_amount':
>         reduction = MIN(scholarship.reduction_value, remaining)
>       remaining = remaining - reduction
>       record_scholarship_application(scholarship, component, reduction)
>       if remaining <= 0:
>         break  // Component fully covered
>   component.final_amount = MAX(remaining, 0)
> ```
> **Key principle:** Percentage scholarships apply to the REMAINING balance, not the original. This is standard accounting practice and prevents over-reduction when stacking a 50% + 50% scholarship (result: 75% total reduction, not 100%).

### 1.4 Year-over-Year Fee Management

**New table: `billing_fee_revisions`**

Tracks fee changes across academic years for audit and compliance.

```sql
CREATE TABLE billing_fee_revisions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  institution_id uuid NOT NULL REFERENCES institutions(id),
  program_id uuid NOT NULL REFERENCES programs(id),
  admission_type text NOT NULL
    CHECK (admission_type IN ('government', 'management', 'nri', 'lateral', 'spot', 'other')),
  from_academic_year_id uuid NOT NULL REFERENCES academic_years(id),
  to_academic_year_id uuid NOT NULL REFERENCES academic_years(id),
  component_name text NOT NULL,                  -- e.g., "Tuition", "Hostel"
  old_amount decimal(12,2) NOT NULL CHECK (old_amount >= 0),
  new_amount decimal(12,2) NOT NULL CHECK (new_amount >= 0),
  change_percentage decimal(7,2) GENERATED ALWAYS AS (
    CASE WHEN old_amount > 0
    THEN ROUND(((new_amount - old_amount) / old_amount) * 100, 2)
    ELSE NULL END                                -- NULL when old_amount=0 (new fee introduced)
  ) STORED,
  justification text,                            -- Required for NAAC
  approved_by uuid REFERENCES profiles(id),
  approved_at timestamptz,
  regulatory_cap_at_time decimal(12,2),          -- What the cap was when revision happened
  created_at timestamptz DEFAULT now()
);
```

### 1.6 Audit Trail (Moved from Phase 6 — MUST be Phase 1)

**New table: `billing_audit_trail`**

All billing operations must be auditable from day one. This table uses Supabase triggers to automatically record every INSERT, UPDATE, and DELETE on all `billing_*` tables.

```sql
CREATE TABLE billing_audit_trail (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  institution_id uuid NOT NULL REFERENCES institutions(id),
  table_name text NOT NULL,                        -- Which billing table was modified
  record_id uuid NOT NULL,                         -- PK of the modified record
  operation text NOT NULL
    CHECK (operation IN ('INSERT', 'UPDATE', 'DELETE')),
  old_data jsonb,                                  -- Previous state (NULL for INSERT)
  new_data jsonb,                                  -- New state (NULL for DELETE)
  changed_fields text[],                           -- Which columns changed (UPDATE only)
  performed_by uuid REFERENCES profiles(id),       -- auth.uid() at time of change
  performed_at timestamptz DEFAULT now(),
  ip_address inet,                                 -- From request headers if available
  context text                                     -- 'admin_ui', 'bulk_generation', 'migration', 'api'
);

-- IMMUTABLE: No updates or deletes allowed on audit trail
ALTER TABLE billing_audit_trail ENABLE ROW LEVEL SECURITY;

CREATE POLICY "audit_insert_only" ON billing_audit_trail
  FOR INSERT WITH CHECK (true);

CREATE POLICY "audit_read_institution" ON billing_audit_trail
  FOR SELECT USING (
    institution_id = auth_institution_id()
    OR EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'super_admin')
  );

-- No UPDATE or DELETE policies = immutable by RLS
```

> **Implementation note:** Create a reusable Supabase trigger function `billing_audit_trigger()` that fires AFTER INSERT/UPDATE/DELETE on every `billing_*` table. Deploy the trigger on all 20 Phase 1-5 tables during their respective migrations. The trigger captures `auth.uid()`, old/new row data as JSONB, and the list of changed columns.
>
> **NULL `auth.uid()` handling:** `performed_by` is intentionally NULLABLE (no NOT NULL constraint). During data migrations, cron jobs, and Edge Function execution, `auth.uid()` returns NULL. The trigger function must handle this gracefully: when `auth.uid()` is NULL, set `context` to `'migration'`, `'cron'`, or `'system'` as appropriate. Application code running with service_role should set a custom GUC variable (`SET LOCAL app.audit_context = 'migration-job'`) that the trigger reads as a fallback identifier when `auth.uid()` is NULL.

## Phase 2: Core Billing Cycle

### 2.1 Bill Generation Engine

**What it does:** Generate accurate, itemized bills for students by looking up their fee matrix and applying scholarships.

**Bill generation flow:**
```
Student Profile (quota + entry_type → admission_type) → Fee Matrix Lookup → Fee Structure → Structure Items → Apply Scholarships → Apply Regulatory Caps → Generate Bill
```

**Enhanced `BillingService` methods:**
```
- generateStudentBill(studentId, academicYearId)
  1. Get student's institution, program, quota, entry_type from learners_profiles
  2. Map to admission_type (see 1.1 mapping note)
  3. Look up billing_fee_matrices for matching entry → get fee_structure_id
  4. Get billing_fee_structure_items for that structure
  5. Check student's billing_student_scholarships → apply reductions in priority order
  6. Validate against regulatory caps
  7. Create billing_student_bills + billing_invoices

- generateBulkBills(institutionId, programId, academicYearId)
  1. Check for existing running job (prevent double-submit)
  2. Get all students in program/year
  3. Group by admission_type
  4. Generate bills per group (skip students who already have a bill for this year)
  5. Report: X bills generated, Y skipped (already billed), Z warnings, W errors
  6. Update job progress in real-time (X/total completed)

>   ON billing_student_bills(student_id, academic_year_id)

```

> **SECURITY MANDATE — Payment callback verification:** ALL payment gateway callbacks (HDFC, Razorpay, or any future gateway) MUST verify the callback signature using HMAC-SHA256 before processing. The verification flow:
> 1. Receive callback payload + signature header
> 2. Compute HMAC-SHA256 of payload using the gateway's shared secret key
> 3. Compare computed hash with received signature (constant-time comparison)
> 4. REJECT the callback if signature does not match — log the attempt, do NOT update any transaction
> 5. Only process the payment update after signature verification passes
>
> The shared secret key MUST be stored in environment variables (never in code or database). Failed verification attempts must be logged with full payload for security audit.

**New table: `billing_offline_payments`**

CREATE TABLE billing_offline_payments (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),

  student_id uuid NOT NULL REFERENCES learners_profiles(id),

  -- Verification

  CHECK (verified_by IS NULL OR verified_by != recorded_by),
  notes text,

  updated_at timestamptz DEFAULT now()

> **Role restriction:** Only users with roles `accountant`, `admin`, `institution_admin`, or `super_admin` can record offline payments. This is enforced via RLS INSERT policy:
> ```sql
> CREATE POLICY "offline_payment_record" ON billing_offline_payments
>   FOR INSERT WITH CHECK (
>     EXISTS (
>       SELECT 1 FROM profiles
>       WHERE id = auth.uid()
>       AND role IN ('accountant', 'admin', 'institution_admin', 'super_admin')
>     )
>     AND institution_id = auth_institution_id()
>   );
> ```
> The `verified_by != recorded_by` CHECK constraint enforces separation of duties — the person who records a cash payment cannot also verify it.

> **`clearance_status` handling by payment mode:** The default `'pending'` is correct for cheques and demand drafts, but misleading for cash/UPI/POS payments where clearance doesn't apply. The application layer MUST set `clearance_status = 'na'` when recording cash, UPI offline, bank transfer, or POS swipe payments. Receipt generation logic should check `clearance_status IN ('cleared', 'na')` before generating receipts.

> **Overpayment validation:** The application layer MUST validate that `amount` does not exceed the bill's current outstanding balance. If an overpayment is genuinely needed (e.g., advance payment), require `institution_admin` or `super_admin` approval with a justification note in `metadata`.

> **Verification role restriction:** The UPDATE RLS policy for `billing_offline_payments` must enforce role restrictions on verification — only `accountant`, `admin`, `institution_admin`, or `super_admin` can set `verified_by`.

**Why a separate table (not just payment_transactions)?** Offline payments have fundamentally different fields:
- Cheque/DD need bank details, clearance tracking, bounce handling
- Cash needs recorded_by (who accepted it) and verification
- Bank transfers need UTR matching
- The workflow is different: record → verify → clear → receipt (vs. initiate → callback → receipt for online)

### 2.6 Program Transfer / Mid-Year Changes

When a student transfers programs mid-year (e.g., B.Tech CSE → B.Tech ECE), the billing must handle the change:

1. **Supersede old bill:** Set `billing_student_bills.status = 'superseded'` on the old program's bill
2. **Generate credit note:** Create a credit record for any amount already paid on the old bill
3. **Generate new bill:** Look up the new program's fee matrix → generate a new bill
4. **Apply credit:** Deduct the credit from the new bill's balance
5. **Net settlement:** If old program was more expensive, issue refund. If cheaper, student has a credit balance.

> **Implementation note:** Add `'superseded'` to the `billing_student_bills.status` CHECK constraint:
> ```sql
> ALTER TABLE billing_student_bills
>   DROP CONSTRAINT IF EXISTS billing_student_bills_status_check;
> ALTER TABLE billing_student_bills
>   ADD CONSTRAINT billing_student_bills_status_check
>   CHECK (status IN ('draft', 'generated', 'partially_paid', 'paid', 'overdue', 'cancelled', 'superseded'));
> ```
> The partial unique index from Phase 2.1 (`unique_active_student_year_bill ... WHERE status NOT IN ('superseded', 'cancelled')`) already handles this — the superseded bill stays in the DB with `status = 'superseded'`, and the new bill passes the partial index check. No additional migration needed for this phase.

  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  institution_id uuid NOT NULL REFERENCES institutions(id),
  student_id uuid NOT NULL REFERENCES learners_profiles(id),
  bill_id uuid NOT NULL REFERENCES billing_student_bills(id),
  step_id uuid NOT NULL REFERENCES billing_escalation_steps(id),
  action_type text NOT NULL,
  status text NOT NULL DEFAULT 'scheduled'
    CHECK (status IN ('scheduled', 'executed', 'skipped', 'approved', 'rejected')),
  executed_at timestamptz,                         -- Set when the action actually runs
  approved_by uuid REFERENCES profiles(id),
  notes text,
  metadata jsonb DEFAULT '{}',
  created_at timestamptz DEFAULT now()
);

-- Prevent duplicate escalation actions for the same student + bill + step
CREATE UNIQUE INDEX unique_escalation_per_step
  ON billing_escalation_log(student_id, bill_id, step_id)
  WHERE status != 'skipped';
```

> **institution_id denormalization:** `billing_escalation_steps` and `billing_escalation_log` carry their own `institution_id` even though it can be derived from the parent policy/bill FK. This is intentional — RLS policies need `institution_id` directly on each table for efficient filtering. Implementation MUST ensure `steps.institution_id = policy.institution_id` and `log.institution_id = bill.institution_id` at insert time.

> **`late_fee_apply` financial recording:** When the escalation engine executes a `late_fee_apply` step, it MUST create a corresponding financial record — not just an escalation log entry. The late fee should be added as a surcharge line item on the student's bill (updating `billing_student_bills.total_amount`) and recorded in `billing_audit_trail`. Without this, late fees exist in escalation-land but never appear on the student's actual bill.

> **Step reordering:** The `UNIQUE(policy_id, step_order)` constraint means reordering steps requires careful handling. Use a transaction with temporary step_order values (e.g., `step_order + 1000`) to avoid UNIQUE violations during swaps, or make the constraint `DEFERRABLE INITIALLY DEFERRED`.

### 5.3b Escalation Safeguards

**Dry-run / Preview mode:** Before activating any escalation policy, the system MUST provide:

1. **Preview mode:** Show exactly which students would be affected, what actions would trigger, and when — without executing anything. Admin reviews the "blast radius" before activation.
2. **Confirmation gate:** Activating a policy that affects >50 students requires explicit confirmation with the count displayed: "This policy will apply to 347 students. Proceed?"
3. **Emergency pause:** Every active escalation policy has a prominent "Pause" button that immediately stops all pending actions. Paused policies retain their state and can be resumed.
4. **Gradual rollout:** New policies can be activated in "pilot mode" — apply to a single section/program first, review results, then expand.

> **Implementation note:** The `billing_escalation_log` already has `status = 'scheduled'` — preview mode generates scheduled entries without executing them. Admin reviews, then confirms execution. Emergency pause sets all `scheduled` entries for that policy to `skipped`.

### 5.4 GST Auto-Calculation

**New tables:** `billing_tax_config`, `billing_tax_calculations`

```sql
CREATE TABLE billing_tax_config (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  institution_id uuid NOT NULL REFERENCES institutions(id),
  tax_type text NOT NULL CHECK (tax_type IN ('gst', 'cess')),
  tax_name text NOT NULL,
  hsn_sac_code text,
  rate_percentage decimal(5,2) NOT NULL,
  applies_to_components text[],                  -- Which fee components are taxable
  is_active boolean DEFAULT true,
  effective_from date NOT NULL,
  effective_to date,
  created_at timestamptz DEFAULT now()
);
```

> **Implementation note:** `applies_to_components` references fee component names as free-text strings (same pattern as `billing_scholarship_rules`). During implementation, validate against actual `billing_item_categories.item_category_name` values. When creating/updating a tax config, validate that no other active config for the same institution + component has an overlapping effective date range.

> **Tax calculation precision:** All tax calculations MUST use exact decimal arithmetic in the application layer (e.g., `Decimal.js` or SQL `ROUND(amount * rate / 100, 2)`). Compute `total_tax` as the literal sum of component amounts (CGST + SGST + IGST), NOT independently calculated, to satisfy the CHECK constraint on `billing_tax_calculations`.

```sql
CREATE TABLE billing_tax_calculations (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  institution_id uuid NOT NULL REFERENCES institutions(id),
  bill_id uuid REFERENCES billing_student_bills(id),
  invoice_id uuid REFERENCES billing_invoices(id),
  tax_config_id uuid REFERENCES billing_tax_config(id),
  base_amount decimal(12,2) NOT NULL,
  cgst_rate decimal(5,2) DEFAULT 0,
  cgst_amount decimal(12,2) DEFAULT 0,
  sgst_rate decimal(5,2) DEFAULT 0,
  sgst_amount decimal(12,2) DEFAULT 0,
  igst_rate decimal(5,2) DEFAULT 0,
  igst_amount decimal(12,2) DEFAULT 0,
  total_tax decimal(12,2) NOT NULL,
  calculation_basis text NOT NULL
    CHECK (calculation_basis IN ('intra_state', 'inter_state')),
  created_at timestamptz DEFAULT now(),
  -- At least one parent reference required
  CHECK (bill_id IS NOT NULL OR invoice_id IS NOT NULL),
  -- total_tax must equal the sum of component taxes
  CHECK (total_tax = cgst_amount + sgst_amount + igst_amount),
  -- CGST+SGST and IGST are mutually exclusive per GST law
  CHECK (
    (calculation_basis = 'intra_state' AND igst_rate = 0 AND igst_amount = 0)
    OR (calculation_basis = 'inter_state' AND cgst_rate = 0 AND cgst_amount = 0 AND sgst_rate = 0 AND sgst_amount = 0)
  )
);
```

## Architectural Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Fee configuration | New `billing_fee_matrices` table | Existing fee structures are line-item level; need a mapping layer for the multi-dimensional matrix |
| Payment gateway | HDFC SmartGateway (existing) | Already integrated. Add Razorpay later only if HDFC can't handle eNACH |
| Offline payments | Separate `billing_offline_payments` table | Different fields and workflow from online. Cheque clearance tracking needs its own model |
| Data migration | Excel/CSV upload with validation | Tally exports to Excel. Build a robust import pipeline |
| Cross-campus analytics | Supabase views + React Query | No separate analytics DB needed at JKKN scale (<10K students) |
| Reminder delivery | Supabase Edge Functions (cron) | Leverage existing WhatsApp/SMS infrastructure |
| Audit trail | Supabase triggers (auto-populate) | Cannot be bypassed by application code |
| Scholarship rules | Separate table from discounts | Different semantics: scholarships are program-level rules; discounts are per-bill adjustments |
| Bill generation | Service layer, not DB trigger | Complex logic (matrix lookup → scholarship apply → cap check) needs application layer |
| Magic strings | CHECK constraints with hardcoded values | Values like `admission_type IN ('government', 'management', ...)` and `regulation_body IN ('state_fee_committee', ...)` are embedded in CHECK constraints. If these need to be admin-configurable in the future, migrate to lookup tables. For now, CHECK constraints enforce data integrity with minimal complexity. |

## RLS Policy Template (All New billing_* Tables)

All new `billing_*` tables created by this spec **MUST** have RLS enabled. Apply during migration creation for each table.

**SELECT / UPDATE / DELETE:**
```sql
CREATE POLICY "institution_access" ON billing_<table_name>
  FOR ALL
  USING (
    institution_id = auth_institution_id()
    OR EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'super_admin')
  );
```

**INSERT:**
```sql
CREATE POLICY "institution_insert" ON billing_<table_name>
  FOR INSERT
  WITH CHECK (
    institution_id = auth_institution_id()
    OR EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'super_admin')
  );
```

> **Note:** `auth_institution_id()` is a STABLE SECURITY INVOKER function that returns `(SELECT institution_id FROM profiles WHERE id = auth.uid() LIMIT 1)`. The `super_admin` bypass applies to ALL operations including INSERT (super_admins may have NULL institution_id in their profile, so they need the bypass to insert for any institution). Student-facing RLS (e.g., students viewing their own bills) requires a separate policy — see Phase 0 audit for the learners_profiles → auth.users mapping.
