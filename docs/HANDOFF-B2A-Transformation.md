> **For:** Developer implementing the full B2A layer on MyJKKN

## Why This Matters

Nicolas Bustamante runs a 6-person company doing what 100+ people did — by routing ALL SaaS through a single AI agent via APIs. His thesis: **every SaaS is now an API endpoint for agents, whether they like it or not.**

MyJKKN has already built 90% of what a B2A platform needs: **40 service modules, 244 RLS-secured tables, 326 API routes, business logic across 44 institutional domains.** What's missing is a door for agents to walk in.

This handoff document specifies how to add that door — turning MyJKKN from a 660-page web app into an **institutional intelligence platform** that both humans (via UI) and agents (via API) can consume.

**One-line summary:** MyJKKN is a B2A platform trapped inside a B2B UI. This document frees the service layer.

### Auth Pattern in API-Management Routes (DUPLICATED 38 TIMES)

Every route under `app/api/api-management/**` repeats this exact pattern inline:

```typescript
// This block is copy-pasted in ALL 38 routes — extract to shared helper
const authHeader = request.headers.get('authorization');
if (!authHeader || !authHeader.startsWith('Bearer ')) {
  return NextResponse.json({ error: 'API key is required' }, { status: 401, headers: corsHeaders });
}
const apiKey = authHeader.substring(7);
const hashedKey = createHash('sha256').update(apiKey).digest('hex');

const supabase = createServerClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL!,
  process.env.SUPABASE_SERVICE_ROLE_KEY!,   // Service role = bypasses RLS
  { cookies: { get() { return undefined; }, set() {}, remove() {} } }
);

const { data: keyData, error: keyError } = await supabase
  .from('api_keys')
  .select('*')
  .eq('key_value', hashedKey)
  .eq('is_active', true)
  .single();

// Check expiry, check permissions.read, update last_used_at
```

**Reference file for this pattern:** `app/api/api-management/organizations/institutions/route.ts`

### Supabase Client Patterns

| Client | File | Use Case |
|--------|------|----------|
| `createClientSupabaseClient()` | `lib/supabase/client.ts` | Browser components (anon key, cookies, RLS) |
| `createServerSupabaseClient()` | `lib/supabase/server.ts` | API routes with user session (anon key, cookies, RLS) |
| `createServiceRoleClient()` | `lib/supabase/server.ts` | Admin operations, **API key routes** (service role key, BYPASSES RLS) |
| `getAuthUser()` | `lib/supabase/server.ts` | Extract user from JWT cookie |

**Critical:** API-key-authenticated routes use the **service role client** because there's no user session. The service role client bypasses RLS entirely. **You must enforce institution scoping at the application level** (WHERE clauses), not rely on RLS.

### Service Layer — Client Mismatch Problem

Most service classes (35 out of 40) use `createClientSupabaseClient()` internally — the browser-side anon key client that depends on user cookies for RLS. This means:

**You CANNOT call most existing service classes from API-key-authenticated routes.**

The exception is `AdmissionService.getDashboardAnalytics()` which accepts an optional external `supabaseClient` parameter.

**Solution for each phase:** Write lightweight adapter functions that execute the same queries using the service role client, OR progressively refactor services to accept an optional external client parameter.

## 3. Phase 1: API Gateway Foundation

**Goal:** Centralized auth, rate limiting, audit logging, and module-scoped permissions. Every subsequent phase depends on this.

### 3.1 Shared API Key Authentication Helper

**Create:** `lib/api-keys/authenticate.ts`

This replaces the 30-line auth block duplicated in 38 routes.

**Function signature:**
```typescript
export async function authenticateApiKey(
  request: NextRequest,
  options?: {
    requiredModule?: ApiModule;
    requireRead?: boolean;    // default: true
    requireWrite?: boolean;   // default: false
  }
): Promise<{ context: ApiKeyContext } | { error: NextResponse }>
```

**`ApiKeyContext` shape:**
```typescript
export interface ApiKeyContext {
  keyId: string;
  keyName: string;
  institutionId: string | null;   // null = all institutions (super key)
  permissions: {
    read: ApiModule[] | true;     // true = legacy all-access
    write: ApiModule[] | true;
  };
  supabase: SupabaseClient;       // Service role client, ready to use
}
```

**Valid modules constant:**
```typescript
export const VALID_MODULES = [
  'admission', 'attendance', 'billing', 'grievance', 'okr',
  'learners', 'staff', 'organizations', 'campus-living', 'solutions',
  'learners-council', 'competency', 'learning-paths', 'alumni',
  'facilitator', 'industry', 'parent-portal', 'social-media',
  'vac', 'maturity-assessment', 'process-excellence', 'notifications',
  'resource-management', 'bug-reports', 'stakeholder-nps', 'audit-trail'
] as const;
export type ApiModule = typeof VALID_MODULES[number];
```

**What it does (step by step):**
1. Extract `Authorization: Bearer <key>` header
2. SHA-256 hash the key
3. Create service role client
4. Look up in `api_keys` table: `key_value = hash AND is_active = true`
5. Check `expires_at` — reject if expired
6. Parse permissions (handle legacy `{ read: true }` and new `{ read: ['admission', 'okr'] }` formats)
7. Check required module against permissions
8. If `institution_id` is set on key AND a different `institutionId` is requested → 403
9. Fire-and-forget update `last_used_at`
10. Return `ApiKeyContext` with service role client ready for queries

**Backward compatibility:** Existing keys with `permissions: { read: true, write: false }` continue to work — `read: true` means "all modules."

### 3.2 New Permission Schema

**Current (legacy):** `{ "read": true, "write": false }`

**New (module-scoped):**
```json
{
  "read": ["admission", "attendance", "billing", "grievance", "okr"],
  "write": []
}
```

No migration needed for the column itself (already JSONB). The `authenticateApiKey` helper handles both formats. New keys should use the array format.

### 3.3 Institution Binding

**Add column to `api_keys`:** `institution_id UUID REFERENCES institutions(id)`

This scopes an API key to ONE institution. If set, the key can only access data from that institution — enforced in the auth helper (not RLS, since we use service role client).

If `institution_id IS NULL`, the key can access any institution (requires `institutionId` as query parameter).

### 3.4 Rate Limiter

**Create:** `lib/api-keys/rate-limiter.ts`

**Approach:** In-memory sliding window (Map-based). Acceptable for MVP — resets on deploy.

```typescript
export function checkRateLimit(apiKeyId: string): {
  allowed: boolean;
  remaining: number;
  resetAt: number;  // Unix timestamp
}
```

**Config:**
- Window: 60 seconds
- Max requests: 60 per key per window
- Cleanup: Every 5 minutes, purge entries older than 2 windows
- Response headers when rate limited: `X-RateLimit-Remaining`, `Retry-After`
- Status code: 429 Too Many Requests

**Future upgrade path:** Redis or Supabase-backed if needed after MVP.

### 3.5 Audit Logger

**Create:** `lib/api-keys/audit-logger.ts`

```typescript
export async function logApiKeyUsage(params: {
  apiKeyId: string;
  endpoint: string;
  module: string;
```

**Behavior:**

## 4. Phase 2: Morning Brief Endpoint

**Goal:** ONE endpoint that proves the B2A model — aggregates read-only data from 5 modules into a single operational briefing.

### 4.1 Morning Brief Service

**Create:** `lib/services/morning-brief/morning-brief-service.ts`

**What it does:** Calls 5 module adapters in parallel using the service role client, returns a unified briefing.

**The 5 modules and their data sources:**

| Module | Data Source | Query Pattern | Key Columns |
|--------|-----------|---------------|-------------|
| **Admission** | `AdmissionService.getDashboardAnalytics()` | Reuse directly (accepts external supabase client) | `institution_id` in filters |
| **Attendance** | `student_attendance` table | Direct query (service doesn't accept external client) | `attendance_date`, `institution_id`, `attendance_data` (JSONB array with `status` field) |
| **Billing** | `billing_student_bills` table | Direct query (no summary method exists) | `final_amount`, `balance_amount`, `status` (unpaid/partially_paid/overdue/paid), `institution_id`, `due_date` |
| **Grievance** | RPC `get_grievance_sla_stats(p_institution_id)` | Direct RPC call | Returns: total_open, total_in_progress, total_resolved, sla_breached, sla_at_risk, avg_resolution_time_hours |
| **OKR** | `okr_objectives` + `okr_check_ins` tables | Direct query | `institution_id`, `status`, `overall_progress` on objectives; `is_completed` on check-ins |

**Return type:**
```typescript

      date: string;

      total_absent: number;
      attendance_percentage: number;
      departments_below_75: number;
    };
    billing?: {
      total_amount_billed: number;
      total_amount_collected: number;
      total_outstanding: number;
      overdue_count: number;
      collection_rate: number;

      total_open: number;
      total_in_progress: number;
      total_resolved: number;
      sla_breached: number;
      sla_at_risk: number;
```

**Module adapter pattern:** Each adapter is a private static method that takes the service role client and institutionId, runs the query, and returns the slim summary type. If a module fails, it logs the error and that module is omitted from the response (not a hard failure).

**Only queries modules the API key has read access to** — checked against `context.permissions.read`.

### 4.2 Morning Brief API Route

**Create:** `app/api/api-management/morning-brief/route.ts`

**Endpoint:** `GET /api/api-management/morning-brief`

**Query params:**
- `institutionId` or `institution_id` — required if key isn't institution-scoped

**Flow:**
1. `authenticateApiKey(request, { requireRead: true })` — shared helper
2. `checkRateLimit(context.keyId)` — 60/min
3. Resolve institutionId (from key binding or query param)
4. If key has `institution_id` and query param differs → 403
5. `MorningBriefService.generateBrief(context.supabase, institutionId, context.permissions.read)`
6. `logApiKeyUsage(...)` — fire-and-forget
7. Return JSON with CORS + rate limit headers

**Response format:**
```json
{
  "data": { ... MorningBriefData ... },
  "meta": {
    "response_time_ms": 342,
    "modules_included": ["admission", "attendance", "grievance", "okr"],
    "modules_skipped": ["billing"],
    "api_key": "Morning Brief - Engineering"
  }
}
```

### 4.3 Existing Precedent

There's already a `admission_daily_briefings` table (migration `20260204130025`) that stores per-user, per-date JSONB briefings. The Morning Brief endpoint is the B2A equivalent — same concept, delivered via API instead of stored in a table.

### 5.2 Route Generator Pattern

Every `/api/b2a/[module]/route.ts` follows the same template:

```typescript
import { NextRequest, NextResponse } from 'next/server';
import { corsHeaders } from '@/lib/api-keys/cors';
import { authenticateApiKey } from '@/lib/api-keys/authenticate';
import { checkRateLimit } from '@/lib/api-keys/rate-limiter';
import { logApiKeyUsage } from '@/lib/api-keys/audit-logger';

export async function OPTIONS() {
  return NextResponse.json({}, { headers: corsHeaders });
}

export async function GET(request: NextRequest) {
  const startTime = Date.now();

  // 1. Auth
  const auth = await authenticateApiKey(request, {
    requiredModule: 'MODULE_NAME',
    requireRead: true,
  });
  if ('error' in auth) return auth.error;
  const { context } = auth;

  // 2. Rate limit
  const rate = checkRateLimit(context.keyId);
  if (!rate.allowed) {
    return NextResponse.json(
      { error: 'Rate limit exceeded' },
      { status: 429, headers: { ...corsHeaders, 'Retry-After': String(Math.ceil((rate.resetAt - Date.now()) / 1000)) } }
    );
  }

  try {
    // 3. Resolve institution
    const institutionId = context.institutionId
      || new URL(request.url).searchParams.get('institutionId');
    if (!institutionId) {
      return NextResponse.json({ error: 'institutionId required' }, { status: 400, headers: corsHeaders });
    }

    // 4. Query (using context.supabase — service role client)
    const { data, error } = await context.supabase
      .from('TABLE_NAME')
      .select('COLUMNS')
      .eq('institution_id', institutionId);

    // 5. Audit
    logApiKeyUsage({
      apiKeyId: context.keyId,
      endpoint: '/api/b2a/MODULE_NAME',
      module: 'MODULE_NAME',
      institutionId,
      statusCode: 200,
      responseTimeMs: Date.now() - startTime,
      request,
    });

    // 6. Return
    return NextResponse.json({ data }, { headers: corsHeaders });
  } catch (error) {
    return NextResponse.json({ error: 'Internal server error' }, { status: 500, headers: corsHeaders });
  }
}
```

### 5.3 Service Adapter Strategy

For each module, you have two options:

**Option A: Direct query** (preferred for read-only)
- Write the Supabase query directly using `context.supabase` (service role client)
- Faster to implement, no risk of breaking existing services
- Use this for simple list/detail endpoints

**Option B: Refactor service to accept external client**
- Add optional `supabaseClient?: SupabaseClient` parameter to the service method
- If provided, use it; otherwise, use the internal client
- Use this for complex business logic (admission analytics, SLA calculations)
- `AdmissionService.getDashboardAnalytics()` already does this — follow that pattern

## 10. Security Model

### 10.1 The Core Principle

**B2A does NOT change WHO can access data. It changes HOW.**

MyJKKN's 244 RLS-protected tables enforce access at the database level. But API-key routes use the **service role client** (bypasses RLS). Therefore:

**ALL access control for B2A routes must be enforced at the application level:**

1. **API key validation** — is the key active, not expired?
2. **Module scoping** — does the key have read access to this module?
3. **Institution scoping** — is the key bound to this institution?
4. **Rate limiting** — is the key within its request quota?
5. **Audit logging** — every request logged with key ID, module, institution, response code

### 10.2 Security Rules

| Rule | Implementation |
|------|---------------|
| Read-only by default | Phase 1-4: NO write endpoints. `permissions.write: []` |
| Institution binding | `api_keys.institution_id` — enforced in auth helper |
| Key rotation | Set `expires_at` when creating keys. Rotate monthly. |
| Key revocation | Set `is_active = false`. Immediate effect. |
| No super keys for agents | Never create keys with `institution_id = NULL` + `write: true` for agent use |
| Audit everything | `api_key_usage_logs` — every request, success or failure |
| CORS | `corsHeaders` from `lib/api-keys/cors.ts`. In production, restrict `Access-Control-Allow-Origin` to specific domains |
| Rate limiting | 60 req/min per key. Prevents bulk exfiltration. |
| No PII in errors | Error responses never include user data, only generic messages |

### 10.3 API Key Tiers

| Tier | Permissions | Use Case | `expires_at` |
|------|------------|----------|-------------|
| **Viewer** | `read: ['morning-brief']` | Management dashboard agent | 90 days |
| **Module Reader** | `read: ['admission', 'attendance']` | Department-specific agent | 30 days |
| **Full Reader** | `read: true` (all modules) | Institutional intelligence agent | 30 days |
| **Writer** | `read: [...], write: ['grievance']` | Phase 3b only — selective writes | 7 days |
| **Super** | `read: true, write: true, institution_id: null` | Platform admin only. NEVER for agents. | 24 hours |

### 10.4 DPDP Act 2023 Considerations

India's Digital Personal Data Protection Act may have specific requirements for automated/agent data processing. Before production launch:
- [ ] Verify if automated access to learner PII requires separate consent
- [ ] Check if agent-generated decisions (via decision_log) need human audit trail
- [ ] Confirm data localization requirements are met (Supabase hosted region)

### 12.3 Institution Resolution Pattern

```typescript
// Resolve institutionId from key binding or query param
function resolveInstitutionId(context: ApiKeyContext, request: NextRequest): string | null {
  const queryId = new URL(request.url).searchParams.get('institutionId')
    || new URL(request.url).searchParams.get('institution_id');

  // Key-bound institution takes priority
  if (context.institutionId) {
    // If query param differs, reject
    if (queryId && queryId !== context.institutionId) return null; // caller returns 403
    return context.institutionId;
  }

  return queryId; // May be null — caller returns 400
}
```

## 14. Glossary

| Term | Meaning |
|------|---------|
| **B2A** | Business-to-Agent — software accessed by AI agents via API, not humans via UI |
| **BFF** | Backend-For-Frontend — API routes that serve the React UI, not external consumers |
| **Service Role Client** | Supabase client using `SUPABASE_SERVICE_ROLE_KEY` — bypasses ALL RLS policies |
| **RLS** | Row-Level Security — PostgreSQL policies that filter data based on authenticated user |
| **Module Scoping** | API key permission that restricts access to specific MyJKKN modules |
| **Institution Binding** | API key bound to one institution — can only access that institution's data |
| **Morning Brief** | Aggregated operational snapshot from 5 modules (Admission, Attendance, Billing, Grievance, OKR) |
| **Context Engine** | Cross-module query system that joins data across multiple modules |
| **Agent Memory** | Persistent storage for agent observations, decisions, and patterns |
| **MCP** | Model Context Protocol — Anthropic's standard for connecting AI models to tools |
| **Adapter** | Lightweight function that runs an existing service's query using a different Supabase client |
