## 2. Permission keys to register

Add to `lib/constants/permissions.ts` `PERMISSION_CATEGORIES` under a `meetings`
module group (create the group if M-series hasn't already):

| Key | Label | Suggested audience |
| --- | --- | --- |
| `meetings.routing.view`   | View routing forms   | Super Admin, Admin, marketing/admission leads, meeting hosts |
| `meetings.routing.manage` | Create & edit routing forms | Super Admin, Admin, the host themselves |

Notes:
- The admin pages gate on `meetings.routing.view` via
  `<PermissionGuard module="meetings" action="routing.view">`. Until the key is
  registered + granted, **super admins still pass** (PermissionGuard super-admin
  bypass), so the pages are verifiable immediately.
- RLS also recognises `host_profile_id = auth.uid()` — a host can always read and
  manage their **own** forms regardless of the `meetings.routing.*` grants. The
  permission keys are for cross-host/institution visibility (leads, admins).
- The migration's RLS policies already reference `meetings.routing.view` /
  `meetings.routing.manage` via `user_has_permission(...)`. Those functions
  return false for unregistered keys (safe default) — registering the keys is
  what activates non-host, non-admin access.

## MANUAL TEST STEPS (after migration applied + types regenerated)

Run the dev server from a `jicate/main` worktree (per CLAUDE.md) once this PR is
merged, or apply the migration to staging and test there.

### A. Admin — build a form

1. Sign in as `test.superadmin@jkkn.ac.in` (password: the value of
   `NEXT_PUBLIC_TEST_PASSWORD` in `.env.local` — set by whoever owns the
   credential, and rotated periodically) at `/auth/test-login`.
2. Go to `/meetings/routing-forms` → click **New routing form**.
3. Title: `Talk to us`. Slug auto-fills `talk-to-us`. Click **Create** → lands on
   the builder.
4. **Fields tab:** add a question — label `What are you interested in?`, type
   `Single choice`, options:
   ```
   Engineering
   Pharmacy
   Something else
   ```
   Toggle **Active (public)** on. Click **Save form** → toast "Form saved."
5. **Rules tab:**
   - Add rule 1: If `What are you interested in?` **is** `Engineering` → **Scheduling
     link** `/book/engineering-admission` (or any `/meet/<handle>`).
   - Add rule 2: If field **is** `Pharmacy` → **External URL**
     `https://www.jkkn.ac.in/pharmacy`.
   - Default ("In all other cases…"): **Message** →
     `Thanks! **Our team** will call you shortly.`
   - Use the **Test routing** panel: type `Engineering` → result shows the
     scheduling link; type `Pharmacy` → external URL; type `Music` → "Default →
     show message".
   - Click **Save rules** → toast "Rules saved."

### B. Public — fill the form

6. Open `/r/talk-to-us` in an incognito window (no login).
7. Confirm the headline/description/question render.
8. Select `Engineering` → **Continue** → you are redirected to the scheduling
   link. (Select `Pharmacy` → external URL; `Something else` → in-page message.)
9. Try `/r/does-not-exist` → explicit "Form not available" page (not a redirect).

### C. Responses

10. Back in the builder → **Responses tab** → each submission appears newest-first
    with its answers + the resolved destination.

### D. Security spot-checks

11. As a non-privileged role (e.g. `test.student@jkkn.ac.in`) hit
    `/meetings/routing-forms` → access-denied card (no list).
12. Confirm anon CANNOT read base tables directly: a raw PostgREST
    `GET /rest/v1/routing_forms` with the anon key returns `[]`/401; only
    `POST /rest/v1/rpc/fn_get_active_routing_form` works for anon.
