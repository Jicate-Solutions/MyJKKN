## 1. Why this sprint exists (customer evidence, not speculation)

**This is the biggest unfinished HR sprint.** Without attendance tracking, Sprint 3's leave workflow has no ground-truth "was the employee actually at work?" data, which is almost certainly why `hr_leave_applications=0` rows exist on production — zero adoption because HR Officers cannot trust leave approvals without parallel attendance reconciliation.

| App Bug (incl. stuck submissions) | 380 | 23.0% | No idempotency, no queue visibility, no retry |

**55% of 1,678 complaints are attendance-related.** Sprint 5 is the project's defining make-or-break per v4 §2.3 ("Attendance engine is the project's defining make-or-break").

## 2. Architecture — the 4-source attendance model

Sprint 5 is **defense-in-depth**. No single source is authoritative. The engine reconciles across four, in this priority order, for every (employee × work_date) cell:

| Priority | Source | Feed | Proof type stored | Failure mode defended |
|---------:|--------|------|-------------------|-----------------------|
| **1** | Biometric punch (eSSL) | Edge agent push → queue ingestion (Sprint 4) | `source='biometric'` | Primary happy-path |
| **2** | Manual punch entry | HR Officer UI (`/hr/attendance/daily`) | `source='manual'`, `reconciled_by` set | Biometric device offline / sync delay |
| **3** | Class-proxy self-heal | If faculty marked any class attendance that day, they were present | `source='proxy'`, `proxy_class_id` FK | Faculty forgot to punch; CCTV evidence common |
| **4** | Employee WhatsApp confirmation | Triggered at 6 PM on missing-out-punch | `source='whatsapp'` | Single-entry-day (the #1 LOP cause above) |

Any employee-day row ends in exactly one of these five terminal states:
`PRESENT`, `HALF_DAY`, `LEAVE` (matched to approved `hr_leave_applications`), `HOLIDAY` (from `institution_leaves` + `hr_work_schedules`), `LOP` (only after all four sources fail).

**Invariant:** LOP is never the default. LOP is only the state arrived at when sources 1–4 all produce no evidence AND `institution_leaves` / `hr_leave_applications` have no match. This inverts the hrapp.co failure: hrapp.co's default was LOP, manual rescue required.

## 3. Schema (3 new tables; 1 reused)

### 3.1 New table — `hr_attendance_records`

The core per-day ground-truth row. One row per (employee × work_date).

```sql
CREATE TABLE hr_attendance_records (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  hr_organization_id  uuid NOT NULL REFERENCES hr_organizations(id),
  institution_id      uuid NOT NULL REFERENCES institutions(id),
  employee_id         uuid NOT NULL REFERENCES staff(id),
  work_date           date NOT NULL,

  -- Terminal state
  status              varchar(20) NOT NULL
                      CHECK (status IN ('PRESENT','HALF_DAY','LEAVE','HOLIDAY','LOP','WEEKLY_OFF')),

  -- Punches
  in_at               timestamptz,        -- first in-punch of day
  out_at              timestamptz,        -- last out-punch of day
  hours_worked        numeric(4,2),       -- computed; null if status != PRESENT/HALF_DAY

  -- Provenance — the defense-in-depth audit
  source              varchar(20) NOT NULL
                      CHECK (source IN ('biometric','manual','proxy','whatsapp','auto_default','policy')),
  proxy_class_id      uuid REFERENCES academic_classes(id), -- populated when source='proxy'
  whatsapp_msg_id     text,                                 -- populated when source='whatsapp'

  -- Reconciliation trail
  reconciled_by       uuid REFERENCES profiles(id),   -- HR officer who accepted/overrode
  reconciled_at       timestamptz,
  reconciliation_note text,

  -- Cross-references (lazy-populated; nullable FKs)
  leave_application_id uuid REFERENCES hr_leave_applications(id),  -- if status='LEAVE'
  holiday_id          uuid REFERENCES institution_leaves(id),      -- if status='HOLIDAY'

  -- Audit
  created_at          timestamptz NOT NULL DEFAULT now(),
  updated_at          timestamptz NOT NULL DEFAULT now(),
  UNIQUE (employee_id, work_date)
);

CREATE INDEX idx_har_org_date    ON hr_attendance_records(hr_organization_id, work_date);
CREATE INDEX idx_har_employee    ON hr_attendance_records(employee_id, work_date DESC);
CREATE INDEX idx_har_lop_pending ON hr_attendance_records(status, work_date)
  WHERE status = 'LOP' AND reconciled_by IS NULL; -- fast "exceptions queue" scan
```

### 3.2 New table — `hr_attendance_regularizations`

Employee-raised requests to correct their own attendance row (e.g., "I forgot to punch out on 14 Feb, here's CCTV").

```sql
CREATE TABLE hr_attendance_regularizations (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  hr_organization_id  uuid NOT NULL REFERENCES hr_organizations(id),
  attendance_record_id uuid NOT NULL REFERENCES hr_attendance_records(id),
  employee_id         uuid NOT NULL REFERENCES staff(id),

  -- Proposed fix
  proposed_status     varchar(20) NOT NULL,
  proposed_in_at      timestamptz,
  proposed_out_at     timestamptz,
  reason              text NOT NULL,
  documents           jsonb DEFAULT '[]'::jsonb,   -- [{name, storage_path, ...}] — CCTV screenshots etc.

  -- Workflow
  status              varchar(20) NOT NULL DEFAULT 'pending'
                      CHECK (status IN ('pending','approved','rejected','escalated')),
  approver_id         uuid REFERENCES profiles(id),
  decided_at          timestamptz,
  rejection_reason    text,

  -- Audit
  idempotency_key     uuid UNIQUE NOT NULL,   -- per v4 §2.2 form submission standard
  created_at          timestamptz NOT NULL DEFAULT now(),
  updated_at          timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_hreg_pending ON hr_attendance_regularizations(hr_organization_id, status)
  WHERE status IN ('pending','escalated');
```

### 3.3 New table — `hr_attendance_exceptions`

Engine-flagged mismatches that HR officers must resolve. Distinct from regularizations (employee-raised) — these are system-raised.

```sql
CREATE TABLE hr_attendance_exceptions (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  hr_organization_id  uuid NOT NULL REFERENCES hr_organizations(id),
  attendance_record_id uuid REFERENCES hr_attendance_records(id),   -- nullable (may precede record creation)
  employee_id         uuid NOT NULL REFERENCES staff(id),
  work_date           date NOT NULL,

  exception_type      varchar(40) NOT NULL
                      CHECK (exception_type IN (
                        'missing_out_punch',       -- triggers WhatsApp flow
                        'missing_in_punch',
                        'single_punch_day',        -- the #1 LOP cause
                        'duplicate_punch_5min',    -- ATT-T7
                        'dst_boundary_anomaly',    -- ATT-T8
                        'approved_leave_no_match', -- leave approved but punch exists — needs review
                        'proxy_conflict',          -- class-proxy present but biometric absent
                        'schedule_mismatch',       -- punch outside hr_work_schedules window
                        'whatsapp_no_reply'        -- self-heal step 2 timed out
                      )),
  severity            varchar(10) NOT NULL DEFAULT 'review'
                      CHECK (severity IN ('info','review','blocker')),
  detail              jsonb NOT NULL DEFAULT '{}'::jsonb,

  status              varchar(20) NOT NULL DEFAULT 'open'
                      CHECK (status IN ('open','resolved','ignored','auto_resolved')),
  resolved_by         uuid REFERENCES profiles(id),
  resolved_at         timestamptz,
  resolution_note     text,

  created_at          timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_hae_open ON hr_attendance_exceptions(hr_organization_id, work_date DESC)
  WHERE status = 'open';
```

### 3.4 Reused — `hr_work_schedules` (Sprint 2, do NOT duplicate)

Sprint 2 already created `hr_work_schedules`. Sprint 5 **reads** it to know: what days is this employee scheduled, what's the shift window, what's weekly-off. Writing into it remains Sprint 2's policy UI (`/hr/policies/hr_work_schedules`).

The Aishwarya-K bug ("Friday shown as auto LOP") is neutralized by making the reconciliation engine MANDATORILY join `hr_work_schedules` before emitting any LOP — no schedule row = exception, not LOP.

## 4. Self-healing missing-punch algorithm (v4 §2.4 verbatim, operationalized)

```text
TRIGGER: Nightly cron at 11:30 PM local — scan hr_attendance_records
         WHERE work_date = today AND in_at IS NOT NULL AND out_at IS NULL

STEP 1 (immediate, 11:30 PM): Class-proxy check
  SELECT 1 FROM academic_class_attendance aca
    WHERE aca.faculty_id = employee.staff_id
      AND aca.marked_at::date = work_date
      AND aca.marked_at > in_at
  → IF FOUND:
      UPDATE hr_attendance_records
        SET status='PRESENT', out_at=aca.marked_at, source='proxy',
            proxy_class_id=aca.class_id
      CLOSE any open exception; no WhatsApp sent.

STEP 2 (if Step 1 found nothing, 6 PM next-open-day): WhatsApp confirmation
  Send template via meta-whatsapp-integration:
    "Hi {name}, no punch-out detected on {work_date}.
     Did you work till {shift_end_from_hr_work_schedules}?
     Reply YES to confirm, NO to dispute (HR will be notified)."
  Record hr_attendance_exceptions row: type='missing_out_punch', severity='review'.

  INBOUND WEBHOOK (idempotent; idempotency_key=whatsapp_msg_id):
    IF YES within 24h:
      UPDATE row: status='PRESENT', out_at=shift_end, source='whatsapp',
                  whatsapp_msg_id=<msg_id>
      CLOSE exception: status='auto_resolved'.
    IF NO within 24h:
      RAISE severity='blocker' on exception; HR officer notification;
      status stays in limbo (NOT LOP) pending review.

STEP 3 (9 AM day-after-work-date, if still no reply): Default + flag
  UPDATE row: status='PRESENT', out_at=shift_end, source='auto_default'
  RAISE exception: type='whatsapp_no_reply', severity='review',
                   detail includes link to row + recommended action.
  Notify HR officer via in-app bell + daily exceptions digest.

NEVER, AT ANY STEP, DEFAULT TO LOP.
LOP only emitted after: full schedule-check, holiday-check, leave-check,
  AND all 4 sources produced nothing.
```

This is the literal inverse of the hrapp.co default-to-LOP behaviour that produced 218 LOP complaints in 22 months.

## 5. Reliability targets (v4 §2.1 + §2.2)

Per `myjkkn-hr-module-spec-v4-evidence.md` §2.1 verbatim: **"99.9% application uptime, <0.1% data loss; edge/device best-effort."**

Sprint 5 engineering contract:

| Invariant | Mechanism |
|-----------|-----------|
| **Idempotency on every punch ingest** | `idempotency_key` UUID; duplicate posts return 200 + existing row, never double-count |
| **Idempotency on every regularization submission** | `hr_attendance_regularizations.idempotency_key UNIQUE NOT NULL` |
| **Queue-based biometric ingestion** | Sprint-4 edge agent already queues; Sprint 5 adds reconciliation-on-drain |
| **Visible submission status** | All mutating APIs return `{ status: 'queued'|'processing'|'sent'|'failed'|'retry_pending', id }` per v4 §2.2 |
| **Daily reconciliation job** | 2 AM cron — replays last 3 days of punches against records; flags drift to `hr_attendance_exceptions` |
| **No silent LOP** | Hard constraint: `status='LOP'` rows REQUIRE `reconciled_by IS NOT NULL` OR `created_at + 72h < now()` (auto-flagged); UI surfaces un-reconciled LOPs as red on daily-grid |
| **DST / timezone safety** | All timestamps stored UTC, displayed `Asia/Kolkata`; ATT-T8 test case mandatory |
